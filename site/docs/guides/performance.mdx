---
title: Performance
description: How the calendar re-renders only what changed, and how stable children, leaf state and cached formatters keep a drop to the rows it touches.
---

A busy week shows thousands of elements: slots, columns, events. The core keeps the layout's
unchanged parts as the same objects, previews are engine view state, and each collection part
calls your children function (in Vue, its slot; in Angular, its template) again only when it has
to. What stays yours is
the framework's usual rule: keep that function stable where a render of your component should not
render the calendar's rows again.

## The layout keeps its identity

`model.get("day-grid")`, `model.get("time-grid")` and `model.get("list")` return layout objects
that keep their identity while nothing in them changed: a week row, a time-grid column, a slot, a
list day and a segment are the same object after an unrelated command. Moving an event makes new
objects only for the rows or columns it leaves and enters; a title change makes new objects for
the rows that show it.

Each part reads its value through a store that keeps the last object while it is equal (React's
`useSyncExternalStore`, a `computed` in Vue and in Angular), so a part re-renders only when what it shows changed.

## The next range reuses the cells

The time grid's column headers, all-day days, slots and columns, and a row's days, are keyed by
their position, not their date: Next, Previous and Today give the same elements (in Angular, the
same views) their new dates, and the framework updates their attributes instead of creating a few
hundred elements again. Your children function is still called for each cell whose layout object
changed, with the new date. State of your own in a cell's component stays with its position: to
start it over with each date, key your element by the date (`key={date}`, `:key="date"`, in
Angular `@for (one of [date]; track one)`).

## When a children function is called again

<Framework name="react">

A collection part (`Weeks`, `Days`, `SlotRows`, `Slots`, `Columns`, `ColumnEvents`, `DayEvents`,
`ListDays`, `ListDay`, `ColumnHeaders`) calls its children function once per entity, and calls it
again for an entity when either changes:

- the entity's layout object (a week row moved an event in), or
- the children function itself (a new function: every entity of the part).

That is React's contract: app state a children function closes over is never stale. An inline
function is a new one on every render of the component that writes it, so that render re-renders
every row of the part. When the component re-renders often (a live region, a field, a status line),
make the function stable.

</Framework>

<Framework name="vue">

A collection part (`Weeks`, `Days`, `SlotRows`, `Slots`, `Columns`, `ColumnEvents`, `DayEvents`,
`ListDays`, `ListDay`, `ColumnHeaders`) calls its default scoped slot once per entity, and calls
it again for an entity when either changes:

- the entity's layout object (a week row moved an event in), or
- the slot itself, when it is not stable.

Vue tracks the reactive state a slot reads in each entity's own render, so app state is never
stale. A template's slot that reads only its scope and reactive state is stable: Vue compiles it
anew on every render, but flags it, and the part calls it through one function for its life, so
only a changed layout object calls it again. A dynamic slot (under `v-for` or `v-if`) or a render
function's slot is compared by identity: a render of the component that writes it renders every
row of the part again.

</Framework>

<Framework name="angular">

A collection (`calendarWeeks`, `calendarDays`, `calendarSlotRows`, `calendarSlots`, and the item
templates of `[calendarColumns]`, `[calendarColumnEvents]`, `[calendarDayEvents]`,
`[calendarListDay]`, `[calendarColumnHeaders]`, and `calendarListDays`) renders its template once
per entity, each entity's view a root view of its own whose context is the layout's objects, and
renders it again for an entity when:

- the entity's layout object changed (a week row moved an event in), or
- the template itself changed (an `@if` that swaps two templates renders every row with the new
  one).

Each entity's view is checked again whenever the template it is in is, so the app state it reads
(a signal, a field) is never stale; with the root's one tick per model commit, a drop or a key's
move is on screen before the next task.

</Framework>

## Stable children functions

<Framework name="react">

A function that reads only its arguments can live outside the component. It never changes, so a
re-render of the component re-renders no row:

```tsx
import { Calendar, type TimeGridColumn } from "@fragiola/calendar-react";

function dayColumn(column: TimeGridColumn) {
    return (
        <Calendar.Column column={column} className="relative flex-1">
            <Calendar.ColumnEvents>
                {(segment) => <Calendar.TimeEvent segment={segment} />}
            </Calendar.ColumnEvents>
        </Calendar.Column>
    );
}

function Week() {
    return (
        <Calendar.TimeGrid aria-label="Week">
            {/* slot rows */}
            <Calendar.Columns>{dayColumn}</Calendar.Columns>
        </Calendar.TimeGrid>
    );
}
```

A function that reads app state takes `useCallback` with that state as a dependency: the rows
re-render when it changes, and only the touched rows when the layout does.

```tsx
import { Calendar, type DayGridWeek } from "@fragiola/calendar-react";
import { useCallback } from "react";

function Month({ highlighted }: { highlighted: string | null }) {
    const week = useCallback(
        (week: DayGridWeek) => (
            <Calendar.Week week={week}>
                {(day) => (
                    <Calendar.Day day={day}>
                        <Calendar.DayEvents>
                            {(segment) => (
                                <Calendar.Segment
                                    segment={segment}
                                    data-highlighted={
                                        segment.eventId === highlighted
                                            ? ""
                                            : undefined
                                    }
                                />
                            )}
                        </Calendar.DayEvents>
                    </Calendar.Day>
                )}
            </Calendar.Week>
        ),
        [highlighted],
    );
    return (
        <Calendar.DayGrid aria-label="Month">
            <Calendar.Weeks>{week}</Calendar.Weeks>
        </Calendar.DayGrid>
    );
}
```

The functions nested inside a row (`Days`, `DayEvents` here) can stay inline: they are written
again only when their row is.

</Framework>

<Framework name="vue">

A template needs nothing more: its slots are stable, and one that reads app state (a `ref`, a
prop) renders again only the rows that read it, when it changes.

```vue title="month.vue"
<script setup lang="ts">
import { Calendar } from "@fragiola/calendar-vue";

defineProps<{ highlighted: string | null }>();
</script>

<template>
    <Calendar.DayGrid aria-label="Month">
        <Calendar.Weeks v-slot="{ week }">
            <Calendar.Week :week="week">
                <template #day="{ day }">
                    <Calendar.Day :day="day">
                        <Calendar.DayEvents v-slot="{ segment }">
                            <Calendar.Segment
                                :segment="segment"
                                :data-highlighted="segment.eventId === highlighted ? '' : undefined"
                            />
                        </Calendar.DayEvents>
                    </Calendar.Day>
                </template>
            </Calendar.Week>
        </Calendar.Weeks>
    </Calendar.DayGrid>
</template>
```

Keep a part's slot out of a `v-if` or `v-for` (put the condition inside it), and in a render
function mark the slots stable with `$stable: true`, which Vue otherwise wraps anew on every
render:

```ts
import { Calendar, type TimeGridColumn } from "@fragiola/calendar-vue";
import { h } from "vue";

h(Calendar.Columns, null, {
    default: ({ column }: { column: TimeGridColumn }) => h(Calendar.Column, { column }),
    $stable: true,
});
```

</Framework>

<Framework name="angular">

A template needs nothing more: one that reads app state (a signal, an input) is checked with its
component, and renders again only the bindings that changed.

```html title="month.html"
<div calendarDayGrid aria-label="Month">
    <ng-template calendarWeeks let-week>
        <div [calendarWeek]="week">
            <ng-template calendarDays let-day>
                <div [calendarDay]="day">
                    <div calendarDayEvents>
                        <ng-template calendarDayEventsItem let-segment>
                            <div
                                [calendarSegment]="segment"
                                [attr.data-highlighted]="segment.eventId === highlighted() ? '' : null"
                            ></div>
                        </ng-template>
                    </div>
                </div>
            </ng-template>
        </div>
    </ng-template>
</div>
```

Keep one template per collection: a template swapped by an `@if` or an `@switch` is another
template, and every row renders again with it. Put the condition inside the template instead.

</Framework>

## State near the leaves

A component re-renders with its own state. When the component holding the calendar keeps the
text of a status line, the edit a dialog is waiting for, or the last announcement, each of them
re-renders the calendar's parts that are its children, up to every row whose children function is
inline. Keep such state in the leaf that shows it: the dialog holds its pending edit, the status
line its text, and the calendar's callback only tells them.

<Framework name="react">

```tsx
import {
    Calendar,
    type CalendarEngineEventOf,
    type CalendarModel,
} from "@fragiola/calendar-react";
import { type Ref, useImperativeHandle, useRef, useState } from "react";

interface StatusLine {
    show(text: string): void;
}

/** The last drop in words: its text is its own state. */
function DropStatus({ ref }: { ref: Ref<StatusLine> }) {
    const [text, setText] = useState("");
    useImperativeHandle(ref, () => ({ show: setText }), []);
    return <p role="status">{text}</p>;
}

function Planner({ model }: { model: CalendarModel }) {
    const status = useRef<StatusLine>(null);
    return (
        <Calendar.Root
            model={model}
            onEventDrop={(event: CalendarEngineEventOf<"drop">) =>
                status.current?.show(`Moved ${event.eventId}`)
            }
        >
            <DropStatus ref={status} />
            {/* the grid: a drop re-renders the line, not the grid */}
        </Calendar.Root>
    );
}
```

A dialog that asks before an edit runs installs its middleware itself
(`useEffect(() => model.use(...), [model])`, the model from `useCalendar()`) and keeps the
waiting edit in its own state: the `recurring-events` and `team-planner` examples do.

</Framework>

<Framework name="vue">

```vue title="drop-status.vue"
<script setup lang="ts">
import { ref } from "vue";

// the last drop in words: its text is its own state
const text = ref("");
defineExpose({ show: (next: string) => (text.value = next) });
</script>

<template>
    <p role="status">{{ text }}</p>
</template>
```

The component holding the calendar calls it through a template ref
(`useTemplateRef("status")`, `status.value?.show(...)` in `@event-drop`). A dialog that asks
before an edit runs takes the model from `useCalendar()`, installs its middleware
(`onBeforeUnmount(model.use(...))`) and keeps the waiting edit in its own `ref`.

</Framework>

<Framework name="angular">

```ts title="drop-status.ts"
import { Component, signal } from "@angular/core";

// the last drop in words: its text is its own state
@Component({
    selector: "app-drop-status",
    template: `<p role="status">{{ text() }}</p>`,
})
export class DropStatus {
    protected readonly text = signal("");

    show(text: string) {
        this.text.set(text);
    }
}
```

The component holding the calendar reaches it with `viewChild.required(DropStatus)` and calls
`show` from `(eventDrop)`. A dialog that asks before an edit runs takes the model from
`injectCalendar()`, installs its middleware in an `effect` (its cleanup removes it) and keeps
the waiting edit in its own signal.

</Framework>

## Cached formatters

Building an `Intl.DateTimeFormat` costs far more than formatting with one, and an event's time
is formatted on every render of every event: a drop renders several, a preview moving renders
its label on each move. Keep one formatter per locale and options:

```ts
const formatters = new Map<string, Intl.DateTimeFormat>();

export function dateTimeFormat(
    locale: string | undefined,
    options: Intl.DateTimeFormatOptions,
): Intl.DateTimeFormat {
    const key = `${locale ?? ""} ${JSON.stringify(options)}`;
    let format = formatters.get(key);
    if (!format) {
        format = new Intl.DateTimeFormat(locale, options);
        formatters.set(key, format);
    }
    return format;
}
```

The examples' `_kit/format.ts` does this for every text they format. The calendar's own text
(`get("title-parts")`, `useDayHeader`, `slot-label-by`) is already formatted with kept
formatters.

## Previews cost nothing to the model

A drag, a resize and a selection preview through engine view state (`engine.get("drag-preview")`,
`"resize-preview"`, `"selection-preview"`): no command runs while the pointer moves, and only the
parts that show the preview (`DragPreview`, `Selection`) re-render. The model receives one
command on the drop. Hit-testing reads boxes measured once per press.

The engine tells the adapter what each change reaches (a `ViewChange`: `focus`, `gesture`,
`preview`, `selection`, `layout`), once per pointer move or key, and keeps each part's attributes
as the same object while they are the same: a preview moving reads no part again. Each adapter
reads a part again only for the changes that may reach it (`engine.adapter.affects`): React's
store skips the part's snapshot, Vue and Angular bump only the revision the part's `computed`
reads. A preview moving re-renders the preview where it is and the one where it was, not the
other days' previews, the slots or the events. The core builds
no `Intl` formatter while the pointer moves: the host's zone (`timeZone: "local"`) is read once and
again at the engine's midnight refresh, and every formatter, "today" and zone check is kept.

## Measured

The playground's stress fixture holds 2 000 events with every feature installed, with stable row
and column functions and a counter in each. Moving one event in the month view re-renders the two
week rows it leaves and enters; in the week view, the two columns. No other row or column renders
again, and the end-to-end tests check those counts.

Each adapter's tests hold budgets on a busy week with the drag-and-resize example's parts and
stable children functions (`tests/render-counts.test.*`):

| | React | Vue | Angular |
| --- | --- | --- | --- |
| 30 preview changes: renders (views checked) | 92 | 62 | 2 |
| 30 preview changes: attribute reads | 90 | 30 | 30 |
| the drop: renders (views checked) | 84 | 76 | 101 |

The drop renders the two columns, their events and previews, the grid's collections and the slot
rows that call their two changed days again (in Angular, each slot cell is a view of its own: the
96 cells of the two days are checked). Angular tells the engine a render committed
(`committed()`) only after a render that touched the calendar: a render of the app's other
state measures nothing.

The examples hold time budgets in the browser, with the CPU slowed four times (about a
mid-range phone): a week or a month drag of `drag-and-resize` runs at 60 fps (a frame's p95 at
most 20 ms, no long task over 50 ms), the dropped event is on screen within 50 ms of the release,
`recurring-events`' scope dialog within 100 ms of the drop (150 ms in a host page that
promotes the frame over its page), and Next in `week` paints the next week within 50 ms. Each framework's end-to-end suite checks them
(`examples/shared/e2e/perf.spec.ts`).

## Other costs that are yours

- `dayMaxEvents` caps a day's lanes (`"auto"` measures them), so a busy month renders a few events
  a day and a "+N more".
- The time grid's slot range (`slotMinTime`, `slotMaxTime`) and `slotDuration` decide how many
  slot rows there are.
- Event content is your component: keep it light, and read the model through `useCalendar` in the
  component rather than in the function (or slot) that renders it.
